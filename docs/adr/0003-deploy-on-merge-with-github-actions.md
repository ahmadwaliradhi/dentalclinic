# Deploy from GitHub Actions on merge, with migrations before the upload

GitHub Actions is the only path to production: every pull request runs the checks, and a push to `main` deploys the `dentalclinic` Worker only after both check jobs pass. The deploy job builds, then applies pending D1 migrations with `--remote`, then uploads, because a broken build must never migrate the production database and an additive migration must land before the code that reads the new column. Pull requests get no preview deployment: there is one D1 database, so preview code would read and write clinic data, and a second database would need its own migrations and seed before it showed anything real; reviewers get the dry-run packaging check instead. Remote seeding stays a deliberate human step (`npm run db:seed -- --remote`) rather than part of every deploy, because `db/seed.sql` will hold fictional patient and clinic records that should not be replayed against production on each merge. Credentials are two repository secrets, `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, exposed only to the Wrangler steps, and the `production` environment is where a required reviewer goes if automatic deploys ever need to stop.
